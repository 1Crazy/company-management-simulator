## Context

这个变更要从零定义一个“公司经营模拟”网页项目，目标是用纯前端逻辑完成完整的经营回合、状态演算、反馈展示和本地存档。当前仓库没有既有业务代码，因此设计重点不是兼容遗留系统，而是先建立一套可维护、可扩展、可调参的模拟框架，避免后续把经营公式、事件脚本和 UI 状态混写在一起。

核心约束如下：

- 必须是纯前端实现，结果全部在浏览器本地计算。
- 不接 AI 服务、后端接口、账号体系或在线排行榜。
- 要能作为独立网页项目运行，适合静态部署和离线演示。
- 经营结果既要有策略深度，也要保持规则透明，便于后续调平衡。
- 页面样式和交互基线采用 `ui-ux-pro-max` 的检索与筛选结果，不使用随意拼装的通用后台模板。

## Goals / Non-Goals

**Goals:**

- 提供一个可完整游玩的经营循环，支持从开局、决策、结算到胜负判定。
- 让公司状态、市场反馈和财务结果形成稳定闭环，用户能通过策略变化观察长期后果。
- 将模拟引擎、场景配置和前端界面分层，确保规则可测试、可调参、可复用。
- 支持本地存档、读档、重开和难度差异，让项目具备反复游玩的基础能力。
- 用规则模板生成经营解读，确保“为什么涨了/跌了”能在界面上解释清楚。

**Non-Goals:**

- 不实现联机对战、多人协作或排行榜。
- 不实现任何 AI 建议、智能秘书、LLM 事件生成或聊天能力。
- 不追求企业级真实财务建模，首版以“可玩、可理解、可平衡”为优先。
- 不依赖后端做鉴权、云存档、配置下发或数据分析。

## Decisions

### 1. 采用单页前端应用 + 纯 TypeScript 模拟内核

项目应实现为单页网页应用，UI 层负责展示和交互，经营结算逻辑集中在纯 TypeScript 模块中。核心状态变化通过明确的输入动作和结算函数推进，而不是散落在组件事件里。

这样做的原因：

- 经营规则可以脱离 UI 独立测试，便于验证公式和边界情况。
- 后续要扩展新场景、新事件或新报表时，不需要重写界面层。
- 可以明确区分“玩家输入”“系统结算”“历史记录”三类数据。

备选方案：

- 把逻辑直接写在组件里：实现快，但很快会失控，尤其是涉及多部门联动时。
- 使用复杂状态机框架：结构清晰，但当前项目规模下会增加实现成本和认知负担。

### 2. 采用“月度回合制”而不是实时模拟

每个经营周期定义为一个离散回合，推荐用“月”作为默认时间单位。单回合流程拆分为 `计划 -> 校验 -> 结算 -> 复盘 -> 下一回合`。

这样做的原因：

- 用户更容易理解经营变量之间的因果关系。
- 财务、市场、事件和目标里程碑都更容易按回合结算。
- 可以显著降低 UI 操作压力，不需要实时动画或持续后台计算。

备选方案：

- 周回合：反馈更快，但数值噪声更大，玩家不容易看出长期趋势。
- 实时经营：表现更“游戏化”，但会让规则透明度下降，也增加实现复杂度。

### 3. 场景、事件和经营公式全部数据化配置

场景目标、难度系数、事件触发表、行业基准和公式参数应放在独立配置层，而不是硬编码在界面组件中。事件触发可以使用带种子的伪随机数，保证同一场景下结果可复现、可调试。

这样做的原因：

- 平衡性调整会非常频繁，数据化配置比改代码安全得多。
- 可支持多个行业或难度，仅替换配置即可。
- 有利于后续做教程模式、挑战模式和特殊经营事件。

备选方案：

- 直接在结算逻辑中写死参数：短期省事，但调优和排错成本极高。
- 使用完全无种子的随机事件：更“随机”，但难以复盘和验证。

### 4. 报表与经营解读使用规则模板，不生成自由文本

经营分析部分只使用预定义模板、标签和阈值规则，例如“营销投入提高品牌认知，但压缩现金储备”。所有解读都来自本地规则，不做 AI 生成。

这样做的原因：

- 完全满足“纯前端逻辑驱动、不接 AI”的约束。
- 结果可预测、可审查，方便和经营公式保持一致。
- 用户能稳定获得结构化反馈，而不是风格化但不可信的描述。

备选方案：

- 只展示数字不解释：实现简单，但可玩性和可理解性明显不足。
- 接入生成式能力写经营点评：违背当前项目目标，也会引入外部依赖。

### 5. 本地持久化采用版本化快照

存档应保存在浏览器本地，并在每个回合结算后自动保存当前进度，同时允许手动存档到多个槽位。存档数据需要带版本号，便于后续规则升级时识别兼容性。

这样做的原因：

- 纯前端项目最适合直接使用浏览器本地存储。
- 自动存档可以避免用户因误操作丢失较长一局的进度。
- 版本号能帮助后续处理不兼容存档，而不是静默读坏数据。

备选方案：

- IndexedDB：更强大，但首版数据量不大，复杂度没有必要。
- 仅手动存档：实现简单，但体验较差。

### 6. 页面结构围绕“决策区 + 结果区 + 历史区”展开

主界面建议使用三段式布局：决策区负责输入本回合策略，结果区展示关键 KPI 和财务摘要，历史区展示事件、目标进度和趋势曲线。这样可以让用户在一个界面完成“制定策略”和“理解结果”的闭环。

这样做的原因：

- 经营模拟的核心不是单一表单，而是输入与反馈的并置。
- 趋势和事件需要持续可见，否则用户很难形成策略记忆。
- 有利于后续做响应式裁剪：桌面端三栏，移动端折叠成分区卡片。

备选方案：

- 多页面向导式流程：信息隔离太强，用户难以对比决策和结果。
- 纯仪表盘布局：数据多但可操作性弱。

### 7. 视觉系统采用 `ui-ux-pro-max` 的“Data-Dense Dashboard + Financial Dashboard”组合

这次视觉方向不使用默认通用 SaaS 风格，而是明确采用 `ui-ux-pro-max` 检索得到的“数据密集仪表盘”与“财务看板”组合作为基底，再结合经营模拟的游戏化语境做二次约束。

落地规则如下：

- 视觉基调采用经营控制室风格：高信息密度、紧凑网格、清晰 KPI 卡片、趋势图和事件流并置。
- 配色以中性浅底 `#F5F5F5`、信任深蓝 `#003366`、强调琥珀 `#F59E0B`、正文石墨 `#333333` 为主；盈利和亏损分别使用 `#22C55E` 与 `#EF4444`，避免以颜色单独传达信息。
- 字体采用“技术感数字字体 + 高可读正文字体”的组合，优先使用 `JetBrains Mono` 承担指标与标题、`IBM Plex Sans` 承担正文与表单文案；如果实现环境受限，再退回 `Fira Code` + `Fira Sans`。
- 图表优先使用折线图、面积图和现金流瀑布对比，交互上保留 hover tooltip、行高亮、关键数值结算动画，但整体动效保持克制。
- 不使用 emoji 充当图标；所有交互卡片需要 hover/focus 反馈，所有图标按钮必须有可访问名称。

这样做的原因：

- `ui-ux-pro-max` 返回的样式中，“Data-Dense Dashboard”最适合经营模拟的高信息密度场景，“Financial Dashboard”最适合利润、现金流和预算反馈。
- 经营模拟需要“像工具一样清晰、像游戏一样有反馈”，这类组合比纯极简或纯游戏化风格更稳。
- 采用明确的字体、颜色和图表规则后，实现阶段不容易退化成随意拼接的后台页。

备选方案：

- 通用卡片式 SaaS 面板：实现容易，但过于模板化，不足以体现经营沙盘氛围。
- 全暗色控制台：氛围强，但会带来阅读负担和暗色偏置，不适合作为默认方案。

### 8. 可访问性与交互反馈按 `ui-ux-pro-max` 的高优先级 UX 规则执行

界面交互必须遵守以下基线：不能只靠颜色表达状态；图标按钮必须有 `aria-label`；所有表单项必须有可见标签；错误提示必须可被辅助技术感知；键盘导航顺序必须与视觉顺序一致；桌面和移动端都要保留清晰焦点态。

这样做的原因：

- 经营模拟页面会包含大量数字、表单和可点击卡片，可访问性问题如果前期不定规则，后续修复成本很高。
- `ui-ux-pro-max` 的 UX 检索明确把颜色对比、键盘导航、错误播报和标签完整性列为高优先级问题。

备选方案：

- 仅在实现后期补无障碍：容易遗漏核心交互，返工成本高。

## Risks / Trade-offs

- [经营规则过于复杂，后续难以维护] -> 通过模块化公式、事件表和场景配置拆分规则，并在任务中优先补齐模拟引擎测试。
- [数值平衡不好，首版不好玩] -> 先提供少量场景和明确目标，用固定种子跑通多轮模拟，持续调整参数表。
- [本地存档在规则升级后失效] -> 为快照加版本号；发现不兼容时提示用户重新开局，而不是强制迁移错误数据。
- [前端状态和历史报表过多导致界面性能下降] -> 回合结束时只保存结构化快照，界面按需计算派生指标，不重复存放冗余数据。
- [纯规则解读显得机械] -> 在模板层准备多种解释标签和组合策略，保证反馈足够清晰但仍可控。
- [数据密集布局在小屏上变得拥挤] -> 桌面端使用多栏，移动端改为分段堆叠和关键指标优先展示，非核心面板折叠。

## Migration Plan

1. 初始化前端项目骨架，并建立模拟引擎、场景配置、存档模块和页面布局的基础目录。
2. 先实现最小可运行的回合循环和公司状态模型，确保“开局 -> 决策 -> 结算 -> 结束”闭环成立。
3. 接着补齐市场/财务计算、事件系统和经营反馈面板。
4. 最后加入本地存档、难度设置、趋势图表和体验性打磨。

回滚策略：

- 如果实现过程中发现玩法闭环不成立，可以先保留静态 UI 壳子，下线模拟入口或隐藏路由。
- 由于没有后端和共享数据，回滚只影响本地构建产物，不涉及线上数据迁移。

## Open Questions

- 首版默认提供几个预设场景更合适；当前设计按“至少一个新手场景 + 若干扩展场景”推进。
- 是否要在首版加入新手引导；当前变更默认仅提供规则可视化和结果提示，不单独做教学系统。
